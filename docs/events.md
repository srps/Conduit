# Runtime Event Stream — Public Contract (schema v1)

**Status:** Contract. This document specifies the event stream
and observable state files as the **first-class extension surface** of
Conduit. Observer extensions (exporters, notifiers, dashboards) build
against this document — not against the Swift source.

## Stability promise

- The current schema is **v1**. A consumer that sees no explicit version
  marker must assume v1; future schema bumps will stamp themselves in
  `ready.json` / the control-socket `status` response before any breaking
  change ships.
- Within a major schema version, changes are **additive only**: new event
  names, new `kind` values, and new JSON fields may appear; existing fields
  never change type or meaning, and existing event names never change
  semantics. Build consumers that ignore unknown fields, kinds, and names.
- Event `detail` strings are diagnostic text: their *presence* is contract,
  their exact wording is not. Parse the documented `key=value` tokens, not
  sentence structure.

## Where events appear

| Surface | Form | Notes |
| --- | --- | --- |
| `$state-dir/events.ndjson` | One JSON object per line | Rolling, size-capped (default 1 MiB); oldest lines are trimmed. Written atomically per event. |
| `pmctl events [--follow]` | Same NDJSON lines | Reads the file; `--follow` tails it. |
| Control socket `events` command | Same NDJSON lines | Daemon-served. |
| In-app event log / `snapshot.json` | Same objects embedded in snapshots | The UI mirrors the daemon; it does not invent state. |

All file-boundary JSON is produced by `CanonicalJSON.encoder()`:
**timestamps are Unix-epoch seconds as a JSON number** (`Double`), directly
readable by `jq`, Splunk, Datadog, and `date -r`.

## Event object shape

```json
{"timestamp": 1781136000.123, "kind": "auth", "event": "auth.kerberos_fallback_ntlm", "detail": "host=proxy.corp:3128 reason=bad_mech"}
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `timestamp` | number (epoch seconds) | yes | Emission time. |
| `kind` | string enum | yes | Coarse category — see below. |
| `event` | string | yes | Dotted machine name, `<subsystem>.<what_happened>`. The primary dispatch key for consumers. |
| `detail` | string | no | Diagnostic detail, often `key=value` tokens separated by spaces. **Always credential-sanitized** (`Authorization`/`Proxy-Authorization`/cookies/bearer/long-base64 masked, URL userinfo stripped) before it reaches any sink. |
| `typed` | object | no | The typed value behind a migrated `lifecycle.*` name: `{"family": "lifecycle", "lifecycle": {…}}`. Absent on legacy records. Its name, kind and sanitized detail must match the record's; see [Typed lifecycle payloads](#typed-lifecycle-payloads). |

### `kind` values (v1)

`lifecycle`, `routing`, `auth`, `connection`, `health`, `config`, `vpn`.
New kinds may be added; ignore unknown ones.

## Typed lifecycle payloads

Four `lifecycle.*` names carry a typed value as well as the legacy `event`, `kind` and `detail`. The value is the record's optional `typed` field, written on the file and the control wire as `{"family": "lifecycle", "lifecycle": {"type": …}}`. The field is additive, so a v1 reader that ignores unknown fields is unaffected. Every other name stays legacy, including the rest of the `lifecycle` kind (`daemon.ready`, `init`, `platform.*`, `helper.*`, `update.*`). A record without `typed` decodes as a legacy record, and no typed value is derived from its `event` or `detail`.

```json
{"timestamp": 1781136000.123, "kind": "lifecycle", "event": "lifecycle.superseded", "detail": "operation=proxy_start generation=3 current=4 reason=superseded", "typed": {"family": "lifecycle", "lifecycle": {"type": "superseded", "operation": "proxy_start", "generation": 3, "current": 4, "reason": "superseded"}}}
```

| `type` | Event name | Keys | Rules |
| --- | --- | --- | --- |
| `superseded` | `lifecycle.superseded` | `operation`, `generation`, `current`, `reason` | `generation` ≥ 1. With `reason` `superseded`, `current` > `generation`; with `runtime_down`, `current` ≥ `generation`. |
| `coalesced` | `lifecycle.coalesced` | `operation`, `joined` | `joined` ≥ 1. |
| `termination_drain_expired` | `lifecycle.termination_drain_expired` | `deadline_ms` | Integer ≥ 0. |
| `version_changed` | `lifecycle.version_changed` | `from`, `to` | Each is a version token; `from` must not read as a bearer credential (below). |

All numeric typed-payload fields are JSON integers.

- `operation` is one of six: `proxy_start`, `proxy_stop`, `dns_start`, `dns_stop`, `runtime_start`, `runtime_stop`.
- `reason` is one of two: `superseded`, a later start or stop overtook the operation; `runtime_down`, a proxy start's listeners were down when it would have continued.
- A version is 1 to 59 bytes of ASCII letters, digits, `.`, `-`, `+` and `_`. This is a boundary rule, not a semver parse: `0.5.8`, `0.5.8-rc.1+7` and `unbundled` are valid, and a `:`, `/`, `=`, space, quote or non-ASCII byte is not. The limit keeps the rendered `from=<version>` run at 64 bytes, under the 65-byte run the sanitizer masks. `from` may not end in the word `Bearer` (any case) at the start or after `.`, `-` or `+`, because its rendered `from=… to=…` line would be masked as a credential. The producer sanitizes both values, then checks the pair, then requires the rendered line to pass the sanitizer unchanged.
- `detail` is derived from the fields, byte for byte: `operation=… generation=… current=… reason=…`, `operation=… joined=…`, `deadline_ms=…` or `from=… to=…`. The producer sanitizes that derived text; every valid typed payload renders a sanitizer fixed point, and the wire checks agreement.

Producers and readers:

- New `lifecycle.*` records must carry a typed value. The kernel's legacy initializer traps on any `lifecycle.` name, and `scripts/check-event-catalogue.py` fails a `lifecycle.` literal outside `Sources/RuntimeEvents` and the wire's own spelling.
- A `typed` value that is present, even as `null`, must be valid and agree with the record's `event`, `kind` and sanitized `detail`. A disagreement, a bad number, an invalid version pair, or an unknown `type` under a known name fails the record. The control wire keeps a record as bounded display text only when neither its name nor its family and type are known.
- The kernel's own file decoder does not classify unknown families, so it fails a line whose `typed` family it does not know. External consumers should skip such a line as an unknown record.
- When the previous version cannot become a valid pair, no `lifecycle.version_changed` is emitted. `update.state_unreadable` with `reason=unrepresentable_version` is emitted instead, with no raw version. `update-state.json` still records the current version.

## Event catalogue (v1)

Names marked *(planned)* are reserved by the roadmap and will appear with
exactly these semantics; do not repurpose them.

### lifecycle
| Event | Emitted when |
| --- | --- |
| `init` | Ring-buffer placeholder; never meaningful, filter it out. |
| `proxy.starting` / `proxy.stopping` | Orchestrator lifecycle transitions. |
| `daemon.ready` | Daemon runtime host finished startup (`detail: mode=…`). Emitted after launch recovery has finished, so a consumer never sees readiness while a crashed run's settings are still being handed back. |
| `platform.launch_recovery_restored` | Launch-time crash recovery found a surface a run that never tore down left applied, restored the journal's recorded prior values and released it (`surface=systemDNS` or `surface=systemProxy`, `stale=true` when the records were over 7 days old and were restored without a liveness probe). One event per surface per launch from both hosts, in the order system DNS, system proxy, resolver files. Emitted before the log line. |
| `platform.launch_recovery_nothing_to_do` | Recovery had nothing to act on for a surface (`surface=`, `reason=` one of `nothing_recorded`, `already_settled`, `fresh_install`, `no_journal`). |
| `platform.launch_recovery_declined` | Recorded state exists, but a local listener is still serving it, so another session owns the machine and it was left alone (`surface=`, `reason=live_listener`). |
| `platform.launch_recovery_discarded` | System DNS: a resolver answers on `:53` but no interface points at loopback any more, so the records described nothing and were dropped without a write (`surface=systemDNS`, `reason=no_interface_points_at_loopback`). |
| `platform.launch_recovery_adopted` | The one-time resolver-file scan on the first launch of a release that records resolver files (`surface=resolverFile`, `adopted=`, `removed=` whether adopted files were removed because the switch is off, `foreign=` files with other contents left alone, `unjudged=` entry files left in place). |
| `platform.launch_recovery_skipped` | A recovery step was not attempted (`surface=`, `reason=config_unavailable` when the config failed to load, which only the resolver scan needs; `reason=journal_unreadable`). The daemon emits these to `events.ndjson` even when it then exits on a bad config. |
| `platform.launch_recovery_failed` | A restore threw, or part of it did not land and the records were kept for the next launch to retry (`surface=`, `reason=` the error, or `records_kept`). |
| `lifecycle.superseded` | A start or stop stopped short, because a later start or stop had begun in the meantime (`reason=superseded`) or, for a proxy start, the listeners it started were down by then (`reason=runtime_down`). Checked after each suspension; inside its platform work the operation also stops before its next manager step. The later operation owns the surfaces; its work was queued behind this one's. `detail: operation=proxy_start\|proxy_stop\|dns_start\|dns_stop\|runtime_start\|runtime_stop generation=… current=… reason=…`. Typed: see [Typed lifecycle payloads](#typed-lifecycle-payloads). |
| `lifecycle.coalesced` | A start or stop arrived while the same kind of operation was the latest and still running, and joined it instead of queueing a second copy of its platform work (`detail: operation=… joined=<generation>`). Typed: see [Typed lifecycle payloads](#typed-lifecycle-payloads). |
| `lifecycle.termination_drain_expired` | The app's quit waited `deadline_ms` for the platform queue and went ahead with its clears; a step still running is serialised with them by its manager's lock (`detail: deadline_ms=…`). Typed: see [Typed lifecycle payloads](#typed-lifecycle-payloads). |
| `lifecycle.crash_restart` *(planned)* | First startup after an unclean exit; detail references prior exit evidence and the matching crash-report name. |
| `lifecycle.version_changed` | The app launched with a different version than the last launch recorded in `update-state.json` (`detail: from=… to=…`). After an in-app update this is the first event of the relaunched version; a manual install produces it too. Not emitted on a first launch, nor when the previous version cannot be typed (see `update.state_unreadable`). Typed: see [Typed lifecycle payloads](#typed-lifecycle-payloads). |
| `helper.installed` | **Install Helper** in Settings ran the app's bundled `install-helper.sh` (#121). `detail: caller_policy=enforced` (pinned to this build's certificate and the release certificate), `unenforced` (this build is signed ad-hoc, so the pin was removed and any program of the console user is admitted; logged as a warning) or `unchanged` (no app to derive a pin from). |
| `helper.install_failed` | The install from Settings did not complete: the password prompt was dismissed, the app carries no installer, or the installer refused, for example a pin that would not accept this app (`detail: reason=…`). |
| `helper.uninstalled` / `helper.uninstall_failed` | **Uninstall Helper** in Settings removed the helper and its pin, or did not (`detail: reason=…`). |
| `update.check_requested` | The app started the nested updater (`source=user` for "Check for Updates…", `source=schedule` for the daily background check). Recorded as the last check whatever the outcome, so a failing feed is retried at the next interval rather than in a loop. |
| `update.check_unavailable` | A check was asked for in a build that cannot update itself (`source=`, `reason=` no update signing key, no feed, or no bundled updater). |
| `update.launch_failed` | The updater process could not be started (`source=`, `reason=`). |
| `update.available` | Reported by the updater: the feed offers a newer, compatible version whose archive Sparkle will verify against the app's update key (`version=`). |
| `update.up_to_date` | Reported by the updater: nothing newer. |
| `update.failed` | Reported by the updater: the check, download, signature verification or installation failed (`reason=` Sparkle's error domain, code and message; `reason=start …` when Sparkle refused its configuration; `reason=background_check_timeout` after 300 s). |
| `update.installing` | Reported by the updater: the user chose to install and Sparkle is about to quit the app with a normal quit event, so termination cleanup restores proxy and DNS settings before the bundle is replaced (`version=`). The next launch emits `lifecycle.version_changed`. |
| `update.report_rejected` | A message on the updater's channel for this app was malformed or named no known report (`reason=`). Messages addressed to another copy of the app are ignored without an event. |
| `update.preflight_started` / `update.preflight_passed` | An explicit install choice starts a bounded authenticated candidate check, or it passes before Sparkle is permitted to stage installation (`version=`). Checks cover archive/code signatures, expansion, bundle/version, architecture/minimum OS, destination permissions, and candidate helper admission/protocol. |
| `update.preflight_failed` | Candidate verification or compatibility failed before the install choice reaches Sparkle (`version=`, fixed `reason=` category). The serving host remains running. Network errors and child output are not copied into the report. |
| `update.state_unreadable` / `update.state_unwritable` | `update-state.json` could not be read or decoded at launch (the app carries on with no last check and no previous version), or could not be written (`reason=`). A previous version that cannot become a typed `lifecycle.version_changed` is reported here as `reason=unrepresentable_version`, with no raw value (see [Typed lifecycle payloads](#typed-lifecycle-payloads)). |

### routing
| Event | Emitted when |
| --- | --- |
| `transparent_proxy.direct_failed` | An intercepted client's direct origin lookup/connect failed (`host=`, `started_cause=`, `current_cause=`, monotonic `dial_ms=` including lookup, `error=`). Emitted before its log. The paired causes distinguish an off-VPN attempt that outlived reconnection from an attempt started under the current state. |
| `direct_mode.entered` | Routing flipped to direct (`detail` carries the cause). |
| `local_pac.starting` / `local_pac.started` / `local_pac.stopping` / `local_pac.stopped` / `local_pac.restarting` / `local_pac.updated` | Local PAC server lifecycle as a proxy start or config reload reconciles it (`reason=proxy_start` or `config_reload`). `updated` swaps the served script in place; `restarting` replaces a listener whose port changed; `stopping`/`stopped` bracket turning the served PAC off. |
| `local_pac.failed` | The local PAC server did not start (`detail` is the error text). A proxy start fails with it, including the restart of a reload that replaces the listener; a reload that only reconciles the PAC server logs a warning and carries on. |
| `routing.socks5_force_proxy` | A SOCKS5 request matched `routing.forceProxyHosts`, so PAC is skipped and it goes through the upstreams (`detail: host:port`). Not emitted while an intentional direct state routes client traffic directly; that keeps precedence. Logged at debug. |
| `transparent_proxy.direct_fallback` | An intercepted client's CONNECT through the upstream failed and it is relayed direct instead (`host=` the SNI host, `cause=` the current routing cause). The same fallback rule as `HTTPProxyHandler`. Warning log line. |
| `transparent_proxy.blocked` | The same failure, but strict mode forbids the direct fallback under the current cause, so the client connection is closed (`host=`, `cause=`, `reason=strict_mode`). Error log line. |
| `pac.refreshed` | The routing engine installed a freshly fetched PAC (`url=`, credentials stripped). The first install after a `pac.routes_invalidated` adds `after=` with its reason and logs at notice, so the app's `proxy.log` shows the reload. A different script drops every cached answer. The same script as the one loaded ends the detail with `script=unchanged` and keeps them: each is served on its next use and evaluated again in the background. |
| `pac.preview_completed` | Settings evaluated a PAC for a validated Browser Test URL; `target=` and `chain=` describe the answer also shown beside Preview PAC. Evaluation runs off the main thread, with one preview in flight. |
| `pac.preview_failed` | Settings rejected the diagnostic URL or failed to fetch/evaluate the PAC. The error text is also shown beside Preview PAC. An invalid target is rejected before fetching. |
| `pac.refresh_wait_refused` | A caller found a PAC refresh running with 64 callers already waiting on it (`limit=`), so it went on without waiting for the outcome. Only control-plane callers wait, so this marks a runaway caller. |
| `pac.refresh_failed` | A PAC fetch or compile failed; `detail` is the error text. The last working evaluator stays in place, unless `pac.routes_invalidated` dropped it. A fetch that started before a `pac.routes_invalidated` and failed after it ends its `detail` with `superseded=refetching`: it does not count towards the backoff, and the fetch is retried on the new network. |
| `pac.refresh_backoff` | A path-triggered refresh was skipped because the URL is in failure backoff (`failures=`, `remainingSeconds=`). Wake, VPN connect and disconnect, user action and a changed URL bypass it. |
| `pac.routes_invalidated` | The routing engine dropped every answer computed on the network that just changed: the route cache and any evaluation in flight (a background re-evaluation included), and for a VPN transition the loaded script. `reason=vpn_connected` (the VPN came up, at cold start or after an outage), `vpn_disconnected` (it went down for good; a flap does not invalidate) or `network_changed` (a material `network.path_changed`, not the first path); `routes=` cached routes dropped; `script=dropped`, `kept` (`network_changed`: requests are evaluated afresh by the loaded script while it is fetched again) or `none`; `fetch=restarted` when a fetch was running (it installs nothing and fetches again) or `idle`. A forced PAC fetch follows; after a VPN transition it ignores the backoff, after a path change it honours it and is skipped on an unsatisfied path. Until a script loads, requests go through the configured upstreams as `pac.no_usable_route reason=not_loaded`. Only emitted while PAC routing is on; logged at notice. |
| `pac.evaluation_slow` | Running the PAC script for a request took over 500 ms (`host=`, `ms=` the script's own run, not the wait for the evaluator queue, `suppressed=`). At most once per host every 10 minutes, from a table of at most 64 hosts; `suppressed` counts the slow evaluations of that host held back since the previous event. The warning line (`PAC evaluation took Nms for <host>`) is derived from it. A cached answer is served for up to 10 minutes and evaluated again in the background once it is a minute old, so a slow host costs a request its wait only on its first request and after an invalidation. |
| `pac.revalidation_failed` | A background re-evaluation of a cached answer failed or timed out, with no request waiting on it (`host=`, `reason=evaluation_failed` or `timeout`, `suppressed=`). The cached answer goes on being served until its 10 minutes are up and is tried again a minute later. Not emitted when a `pac.routes_invalidated` or a refresh with a different script dropped that answer while the re-evaluation ran. At most once per host every 10 minutes (same table as `pac.evaluation_slow`); logged as a warning. |
| `pac.routes_truncated` | An evaluation exceeded `pacUsableRouteLimit` (default 32, validated 1–128). The first usable routes stay in script order; excess PROXY/DIRECT entries are never attempted or promoted. `retained=`, `dropped=`, `limit=`, `suppressed=` are counts only, without raw PAC text. Globally coalesced to one report per engine per 60 seconds; cache hits do not count as new truncations. Event precedes its warning log. See [`pac-route-bounds.md`](pac-route-bounds.md). |
| `pac.evaluation_refused` | The PAC evaluation queue was full, so a request was answered without evaluating (`host=`, `reason=queue_full` or `waiters_full`, `limit=`). The request is also a `pac.no_usable_route` with `reason=refused`. |
| `pac.no_usable_route` | PAC routing is on but gave a request nothing to route by, so it went through the configured upstreams only: no DIRECT, no direct-reachability shortcut, no PAC direct fallback (`reason=`, `host=`, `rejected=`, `suppressed=`). `reason` is `empty` (no entries, including every entry CFNetwork drops: `HTTPS`, `HTTP`, `SOCKS5`, `QUIC`, unknown words, `""`), `unsupported` (every entry rejected, at least one of a type Conduit cannot use, such as `SOCKS`), `invalid` (every entry rejected for a bad host or port), `evaluation_failed`, `timeout`, `not_loaded` (no script loaded yet), `refused` (see `pac.evaluation_refused`) or `superseded` (the answer came from a PAC the configuration no longer names, or was computed before a `pac.routes_invalidated`). Also emitted with `unsupported`/`invalid` when the only usable entry was a `DIRECT` that followed rejected entries and strict mode suppressed it as a fallback. `rejected` lists the rejected entry types, at most 8, never a host or URL. A chain keeps only its first 8 rejected entries; when it had more, `rejectedTotal=` gives the count (the reason still accounts for all of them). At most one event per reason per minute; `suppressed` counts the requests held back since the previous one. |
| `routing.strict_direct_reachable` | In strict mode a request failed through the upstream (502) because the upstream could not reach its target, and a single direct probe of that target answered (`host=`, `port=`, `hint=add_to_no_proxy_hosts`). Only a transport failure, a timeout, a malformed or interrupted answer, or an upstream 5xx qualifies. An upstream 4xx (such as a 403 policy refusal), an authentication failure (rejected, or no credential or ticket), a client hang-up, and a request refused locally never reached a decision about the target's reachability, so they are not probed. The request still failed; nothing is retried directly. Add the host to No-proxy hosts if it should bypass the proxy. At most one probe, and one event, per host every 10 minutes, and at most 4 probes in flight (further hints are skipped). No probe runs while routing is changing under the proxy; see `routing.strict_direct_reachable_suppressed`. The probe follows the direct path's metadata/loopback policy: in gateway mode a blocked host, or one that resolves to a blocked address, is never connected to and gets no hint. |
| `routing.strict_direct_reachable_suppressed` | In strict mode a request failed through the upstream (502), but no hint probe ran because routing was changing under the proxy, so the failure says nothing about the host (#97). `reason=flap` during a VPN flap hold (`.reasserting`), `direct_mode` while in direct mode, `vpn_transition` while a VPN connect or disconnect is being handled and for 15 s after it, or after a direct-mode change such as upstreams recovering. Also `host=`, `port=` of the failure that emitted it, and `suppressed=` the failures not probed for that reason and transition since the last event, this one included. One event for the first suppressed failure of each reason and transition, then at most one a minute while it lasts; the log line (info) is derived from the event. A suppressed host is not put on its hint cooldown, so its next failure after the window is probed. |
| `routing.probe_blocked` | In gateway mode a direct probe refused to connect under the metadata/loopback blocklist, so its target counts as not directly reachable (`host=`, `port=`, `kind=reachability` for the non-strict reachability shortcut or `strict_hint` for the strict-mode hint, `reason=blocked_name` when the host itself is blocked or `blocked_address` with `address=` when it resolved or connected to a blocked address). Nothing was connected to. At most one event per host every 10 minutes, from a table of at most 256 hosts; the log line is derived from the event. |
| `routing.direct_scheme_rejected` | A non-CONNECT request with an absolute target whose scheme is not `http` or `ws` (typically `https://`) was routed DIRECT, including a DIRECT fallback after an upstream failure, and was refused with a 400 before anything was dialled (`target=`, `scheme=`). The direct path writes plaintext HTTP, so forwarding it would have sent the request's headers and body unencrypted. HTTPS clients use CONNECT, which is unaffected. Emitted before its WARNING log line. |

### auth
| Event | Emitted when |
| --- | --- |
| `auth.kerberos_recovery_started` | An initial leg has a confirmed `KRB5_KDC_UNREACH` cause and attempts independent service-ticket acquisition (`host=`, `reason=kdc_unreachable`, GSS/probe codes). Limited to one attempt per minute across all targets in the runtime auth factory. Runs under the process-wide GSS gate, off NIO loops. App/daemon compositions launch the same signed executable in worker mode; headless tools do not launch workers. |
| `auth.kerberos_recovery_succeeded` | The worker succeeded and the parent retry produced a nonempty token (`host=`). Normal Kerberos outcome reporting follows. |
| `auth.kerberos_recovery_failed` | Independent acquisition or the single parent retry failed (`host=`, `stage=prime` with a bounded worker/command reason, or `stage=retry` with available GSS codes). Existing failure/fallback handling continues. No recursive retry, continuation replay, credential destruction or global cache-notification spoofing. |
| `auth.kerberos_succeeded` | Initial Kerberos leg produced a token (`host=`). |
| `auth.kerberos_fallback_ntlm` | Credential-class Kerberos failure downgraded to NTLM (`host=`, `reason=` one of `no_credential`, `credentials_expired`, `bad_mech`, `failure`, `no_ticket`, `service_ticket_unavailable`, `routine_<n>`; then the GSS codes `major=`, `minor=` (signed, as Kerberos errors are written) and, when the minor is a known Kerberos error, `krb5_error=` such as `KRB5KDC_ERR_S_PRINCIPAL_UNKNOWN` or `KRB5_KDC_UNREACH`; then `suppressed=`). At most once a minute for each host and reason; `suppressed` counts the fallbacks held back since the previous one. The NOTICE log line is derived from the event and follows the same limit; the snapshot's `lastAuthFallbackReason` still follows every fallback. SPNEGO often reports `minor=0` for a Kerberos-mech failure, which names nothing. So for `service_ticket_unavailable`, Conduit makes one diagnostic `gss_init_sec_context` against the raw Kerberos mech for the same SPN, inside the GSS gate, and reports its answer as `krb5_major=` and `krb5_minor=`, with `krb5_error=` naming the mech's minor (not SPNEGO's). If that call could not be made, it reports `krb5_probe=failed`; an undiagnosed minor-zero service-ticket failure reports `krb5_probe=unavailable`. Credential absence has its explicit fallback reason and does not trigger a raw-mechanism probe. The diagnostic call costs a TGS request, so it runs at most once per host a minute, only while the host is failing. Within that interval the latest probe result is retained in a bounded 64-host cache and attached to subsequent failures, so independently timed log gates still carry the cause without another TGS request (`krb5_probe=cached` marks a retained result). Cached diagnostics alone never start a recovery attempt. The diagnostic call alone does not change classification or fallback, and its token is discarded unread. A confirmed KDC-unreachable initial leg may separately trigger the recovery described below. |
| `auth.kerberos_failed` | A Kerberos failure reached the request with no NTLM answer: no saved password, a failure that permits no fallback, or a continuation token GSS rejected (`host=`, `reason=` as above, plus `other`; then `major=`, `minor=` and the `krb5_` fields as above when the failure has GSS codes; then `suppressed=`). At most once a minute for each host and reason; `suppressed` counts the failures held back since the previous one. Not emitted while a missing credential is being retried; `auth.credential_retry` covers that. |
| `auth.ntlm_configured` | NTLM credentials became available to the authenticator stack. |
| `auth.credentials_unavailable` | The saved NTLM password could not be read (`reason=` one of `not_found`, `denied` for a refused or dismissed Keychain prompt, `interaction_not_allowed` for a prompt that could not be shown, `invalid_payload`, `read_pending` when a handshake gave up after 2 s waiting for a read that is still out, typically behind an unanswered Keychain prompt, `status=<n>` for any other Keychain status, or `other`). `source=handshake` with `host=` when a handshake needed it: the NTLM fallback then goes without NTLM, and NTLMv2 mode fails the request. At most once a minute for each host and reason; `suppressed=` counts the reads held back since the last event. `source=proxy_start` when the read at proxy start failed; that read happens only when a password is saved. A missing password is reported here only in NTLMv2 mode; for the fallback, `auth.kerberos_failed` covers it. |

### vpn
| Event | Emitted when |
| --- | --- |
| `vpn.connected` | VPN observer reports an active link; reconnect probes/refresh have completed. |
| `vpn.reconnecting` | The connected signal is about to invalidate old corporate PAC answers and revoke the previous routing cause, before PAC/probe awaits (`prior_cause=`, `pending_cause=`, `probe=pending`). Old answers are invalidated, breaker holds reset, and DNS transports refreshed before the new cause is published. Configured upstreams resume new-client upstream routing immediately; zero upstreams retain unconditional DIRECT. The browser-facing local PAC follows configuration and remains stable across VPN changes. Existing streams remain open, except those whose path the VPN moved (DIRECT tunnels opened while it was down, on a full tunnel), which `vpn.tunnels_migrated` closes. Also emitted at cold connection and flap recovery. |
| `vpn.disconnected.user` / `vpn.disconnected.lost` | Deliberate vs. lost disconnect (drives different recovery posture — see `docs/design-vpn-flap-resilience.md`). Not emitted when a newer VPN report superseded the disconnect's probe (`connectivity.probe_superseded by=transition`); `vpn.connected` is likewise skipped for a superseded reconnect. |
| `vpn.observation_stale` | A VPN report arrived after a newer one (`state=`, `sequence=` its host stamp, `applied=` the newest applied) and is dropped: hosts deliver each report in its own task, so they can land out of order (#155). A dropped report sweeps nothing: the newer report that was applied owns the path sweeps. Emitted before its INFO log line. |
| `vpn.tunnels_migrated` | A confirmed VPN transition closed the tunnels whose path it removed so their clients reconnect at once (#148, #156); a flap never starts a sweep. Path sweeps: `transition=disconnected\|connected\|tunnel_changed phase=paths pass=N upstream_closed= direct_closed= unchecked=`; `tunnel_changed` is a connected VPN moving to another tunnel interface. A socket's path is gone when its local address is no longer assigned or the kernel would now reach its peer through another interface (`SocketPathChecking`). Pass 0 runs at once, without waiting for the connectivity probe; later passes run as routes settle (2 s and 10 s after) and are emitted only when they closed or could not check something. `unchecked=` counts sockets the check could not judge, which are left to their timeouts; the line is then a warning. A flap holds the pending passes and its recovery (a `.connected` report, or a wake that finds the upstream reachable) runs them; with none pending, the recovery runs one address-only pass after the first delay, `transition=flap_recovered phase=addresses pass=1 …`, emitted only when it closed or could not check something. Routing phase, once a disconnect's probe settles routing: `transition=disconnected phase=routing reason=user\|lost\|unknown routing=direct\|upstream upstream_closed=`; with `routing=direct` every remaining upstream channel closes. When a newer VPN report ran while the probe was pending, the stale handler emits `transition=disconnected phase=routing reason= skipped=superseded` and closes nothing. Path sweeps run with the listener stopped (a restart preserves tunnels); the routing phase then runs once the start probe commits routing. A request whose connection a sweep closed fails locally (`vpnTransitionDuringConnect`) without a retry on a fresh upstream connection or a failure event. A dial that connects over a removed path is reported on its own, as `connection.late_dial_retired`. |
| `vpn.flap.start` / `vpn.flap.recovered` | Debounced flap window opened / closed (`detail` carries durations and preserved-stream counts). |

## Consumer guidance

- Dispatch on `event` (exact match), group on `kind`.
- Tail with rotation-awareness: the file is trimmed in place (rewritten
  atomically), so `tail -F` (capital F) semantics are required.
- Never assume an event you depend on is the *only* signal: snapshots are
  the state of record; events are the change log.
- The sanitizer is the last line of defense, not an invitation: if you
  build an exporter, do not log `detail` into systems with weaker access
  controls than the user's own machine without review.
