# 0045: DoH reaches the upstream only through Conduit, and DoH and PAC sessions never hand a proxy challenge to macOS

- Date: 2026-11-11
- Decision: proposed
- Implementation: implemented
- Validation: pending
- Supersedes: none
- Superseded by: none

The owner approved this decision on 2026-11-11, before the pull request existed, and approved the upstream route and the narrowed scope in review of that pull request the same day. A second review round the same day gave the route a pool of its own that does not count an answered 4xx, made its stop close the connections it accepted, and made admission compare parsed hosts. A third round the same day made admission refuse any spelling but a strict one and dial the configured provider rather than the client's text, made the route's stop fence every later dial and retry, and made one tunnel try each upstream at most once. A fourth round the same day made a selection own the half-open probe slot it claims, kept a failover off any upstream in its backoff, charged a refused tunnel dial, read the stop's fence under the pool's lock, limited the report of a refused tunnel target, and refused a port tunnel's non-ASCII remote host at the config boundary. It stays proposed until the owner confirms it on the pull request.

## Context

On the first full-tunnel VPN connect, Conduit 0.6.2 made macOS show an "authenticate to the proxy server" dialog for the Conduit process. The macOS log showed the cause. CFNetwork tasks with the DoH timeouts (4 s request, 8 s resource, `DoHSessionFactory.requestTimeout`) logged "Fetching proxy credential". Then `AuthBrokerAgent` logged "Prompting user" for Conduit's process ID.

The DNS forwarder and the transparent proxy's origin resolver race each DoH lookup over several routes. One of these routes sent the lookup straight to the first enabled upstream proxy, through a `URLSession` with no delegate. When the upstream answers 407, a session with no delegate lets CFNetwork authenticate by itself. CFNetwork asks `AuthBrokerAgent` for a saved proxy credential. On the first connect there is no Kerberos service ticket yet, so the saved credential fails, and macOS prompts the user.

Removing that route left two: direct, and Conduit's client listener. The client listener applies the client routing rules. When PAC answers DIRECT for a DoH provider, a bypass entry matches it, or Conduit is in direct mode, the listener's tunnel goes direct too. Under a full-tunnel VPN that drops direct 443 to a public resolver, every DoH route is then a black hole for as long as the rule holds. `pm-dns` runs no client listener, so it had the direct route only.

## Decision

- DoH lookups have three routes, raced together: direct, Conduit's client listener, and the upstream route. No route names an upstream proxy to `URLSession`.
- The upstream route is a loopback SOCKS listener on an ephemeral port (`DoHUpstreamRoute`). The DNS forwarder binds it when it starts and closes it when it stops. It applies no PAC, bypass or direct-mode rule: it tunnels through an upstream proxy or fails. It dials through a `CONNECTCoordinator`, so the upstream's 407 is answered by Conduit's own Kerberos/NTLM authenticator and a failing upstream fails over, as for every other tunnel.
- The route dials through a `ConnectionPool` of its own, with its own coordinator and auth-handshake limiter. No other traffic uses that pool, so what DoH learns about an upstream cannot open a circuit breaker or move the preferred upstream for port tunnels, the transparent proxy or client traffic. Its breakers are reset when the VPN comes back, with the other pools'.
- That pool does not count an answered 4xx against an upstream. A 5xx, a rejected authentication, a failed connect and a silence still count. See Alternatives.
- One tunnel tries each enabled upstream at most once. Each failover attempt selects among the upstreams that tunnel has not tried, as every `CONNECTCoordinator` tunnel does, so an upstream with a fast latency score that refuses a provider cannot keep the others from being asked.
- A failover asks only an untried upstream the pool may ask now: its breaker is closed, or its backoff has elapsed and no other attempt holds its probe. With none, the failure that led to the failover stands. Only a request's first pick has the last resort that forces the longest-open breaker into a half-open probe when no upstream may be asked, so a failover never skips an upstream's backoff.
- A selection (`UpstreamSelection`) owns the half-open probe slot it claimed, and its attempt settles that claim once. A success or a counted failure is a verdict on the upstream and settles it. Every exit with no verdict gives back that claim and no other: a tunnel given up before or during its dial or handshake, a capacity refusal, another local refusal, an answered 4xx this pool does not count, and a silence that does not count. A refused or failed TCP dial for a tunnel is a failed connect and counts, as it already did for a pooled exchange.
- The route admits a connection only to a configured DoH provider's own host and port. Anything else is refused with `dns.doh_upstream_route_refused` and nothing is dialled. A requested host that holds anything but ASCII letters, digits and `.-_:[]` is refused before it is parsed. An admitted request is dialled as the matching provider's host and port from the config (a name lowercased, in punycode and with the root dot the URL writes; an IPv4-mapped address as dotted-quad), never as the client spelled it, so the CONNECT line and the route's events carry only configured spellings. Admission is an allowlist of hosts as the provider URLs write them, not a pin on addresses. For a provider configured by name, the upstream resolves the name, so the provider's DNS decides where the route connects. The shipped providers are IP literals.
- Hosts are compared parsed, not as text (`DoHProviderHost`). A trailing DNS dot, letter case, a Unicode name in the config and its punycode form in the request, and an IPv4 address and its IPv4-mapped IPv6 form are one host. An IPv4 address is strict dotted-quad: four decimal octets with no leading zero. A short, octal, hex or numeric form, or an address followed by a space and more, which Darwin's `inet_aton` still reads as an address, names no host and is refused. A name still matches exactly. A provider on this machine (loopback, the unspecified address, a `localhost` name) is never raced on the route, because an upstream asked for it would dial itself.
- When the route stops, it closes every connection it accepted (a tunnel in use, one still in its handshake, one waiting on its upstream) and what its pool still holds. The stop first fences every tunnel the listener started: from then on nothing is selected, dialled, retried or added to the pool for it. A CONNECT the stop cut short is not retried on the next upstream, a dial that connects after the stop is closed before it sends anything, and neither is charged to the upstream. A request read after the stop began dials nothing. The fence is read under the pool's lock as a dial joins the pool, the lock the stop's `closeAll` takes, so a dial that connects as the stop lands is either refused there or in the pool when `closeAll` closes it. A handshake that completes after the stop is closed and not handed over.
- The transparent proxy's origin resolver gets the upstream route only while the DNS forwarder runs. The forwarder owns the listener, and the resolver reads its port from the forwarder. With the forwarder stopped the resolver has the direct and client-listener routes only.
- The route is absent when no upstream is enabled. The app also withholds it while client traffic is routed direct because the VPN is off (`DirectModeCause.vpnDisconnected`) or no upstream is configured: Conduit dials no upstream in those states, and direct DoH works there. It stays offered in every other state, including the transient direct mode after a VPN connect.
- `pm-dns` builds a pool and coordinator of its own, as `pm-tunnel` does, and offers the route whenever its config enables an upstream.
- A DoH session, an origin-resolver session and the PAC download session cancel a proxy-authentication challenge with `.cancelAuthenticationChallenge`, whatever its scheme. Every other challenge, such as server trust or a server's own 401, keeps CFNetwork's default handling.
- Each refusal is reported. A DoH or origin-resolver session emits `auth.proxy_challenge_refused` (`client=`, `proxy=`, `method=`, `suppressed=`), at most once a minute per client, proxy and scheme, with a warning log line derived from it, and the forwarder's "all DoH providers failed" warning names the refusal. A PAC fetch fails with an error that names the refusal, and that error reaches `pac.refresh_failed` or `pac.preview_failed`.
- The update download is outside this decision and keeps CFNetwork's default challenge handling. See Alternatives.

## Alternatives

- Keep the direct-to-upstream route and add only the challenge guard. The guard stops the prompt, but every DoH lookup on that route would still meet a 407 and fail.
- Two routes only, direct and the client listener. This was the first form of this decision. It leaves DoH dependent on client routing rules, as Context describes.
- Make the client listener force DoH providers through the upstream. That changes routing for every client that talks to those hosts, a browser's own DoH included, against the rules the user configured.
- An HTTP CONNECT listener for the upstream route. It needs a new listener and handler, where SOCKS reuses the existing `SOCKS5Server` with one routing mode added. An HTTP proxy hop also has a response in which a 407 could one day reach CFNetwork; a SOCKS hop with no authentication has none. And CONNECT carries only `https` providers, so no test without a TLS server could show an answered lookup through it. Measured on macOS 26: `URLSession` greets a SOCKS proxy offering only "no authentication", sends a provider's hostname unresolved, and sends nothing before the SOCKS reply.
- A fixed local port relayed to one provider, as `TunnelForwarder` does. `URLSession` would connect to a loopback address, so the provider's TLS name would not match.
- Dial the route through the pool that port tunnels and the transparent proxy share. This was the first form of the route. Every failed CONNECT for a provider fed that pool's breakers and moved its preferred upstream. A proxy that blocks DoH by policy answers 403 for the default providers, so a few lookups opened the breaker on every upstream and moved tunnel and transparent traffic off a healthy primary.
- Count an answered 4xx against the upstream in the route's own pool. The upstream answered, so it is reachable and authenticating. The route only ever asks for a few fixed providers, so a policy block would open every breaker on a healthy proxy and report `upstream.circuit_opened` for it every open interval, for no gain: each tunnel already tries every upstream once. Not counting a 4xx does not leave the order alone, though. A refused tunnel fails over, and the upstream it fails over to becomes the pool's preferred one, as for any failover. A 5xx is the upstream failing to do its job, so it counts.
- Free whatever probe slot an upstream holds when an attempt ends with no verdict. This was the third round's form. An attempt that never claimed the slot, such as a PAC-chain tunnel naming the upstream itself, could free the slot another attempt's probe held, and a second probe could start beside it.
- Let a failover use the first pick's last resort. This was the third round's form too. With one healthy upstream refusing a target by policy and another in its backoff, the failover forced the one in backoff into a probe and waited out its silence, where the client had failed at once before.
- Rotate the preferred upstream on a failover and let the chooser pick again. This was the coordinator's failover before this decision. The chooser compares two candidates by latency score, and with two upstreams those are always both, so an upstream with a fast score that answers 403 was picked on every attempt and a working one with no score was never dialled.
- `.rejectProtectionSpace`. CFNetwork then offers the proxy's next scheme, and after the last one CFNetwork decides what happens. Cancelling ends the task at once.
- Answer the challenge with Conduit's own credentials. That would be a second authentication path beside the pool's, with its own Kerberos and NTLM state.
- Guard the update download as well. An earlier form of this decision did. It refused an update behind an authenticating system proxy that is not Conduit's listener, where macOS's saved credential would have worked. Sparkle's own sessions run in the same updater process and are Sparkle's code, so the guard did not stop a prompt there. And an update is something the user asked for, so a credential prompt during one is expected, where a prompt from a background DNS lookup is not.

## Consequences

- No macOS proxy-credential prompt comes from a DoH lookup or a PAC download.
- A routing rule that sends a DoH provider DIRECT no longer makes public names unresolvable under a VPN that drops direct 443. This also covers the transient direct mode after a VPN connect, which the first form of this decision accepted as a few seconds of failed lookups.
- The DoH race starts three routes per provider and encoding while an upstream is in play. Each lookup can open tunnels in the route's pool, within that pool's connection limit.
- Pool and 4xx policy chosen: the route has a pool of its own, and that pool counts a 5xx, a rejected authentication, a failed connect and a silence against an upstream, but not an answered 4xx. A refused tunnel still moves the route pool's preferred upstream to the one it failed over to. The tunnels' pool and the client listener's pool keep counting every answered status, as before.
- Every `CONNECTCoordinator` tunnel, not only the route's, now asks each enabled upstream at most once and fails over to one it has not tried and the pool may ask now. Before, a failover could ask the same upstream again.
- In every pool, a tunnel whose TCP dial to the upstream is refused or times out now counts as a failed connect, as a pooled exchange's already did. Before, it counted nothing, and a half-open probe that met it held the probe slot until a reset.
- A port tunnel whose `remoteHost` holds anything but ASCII letters, digits and `.-_:[]` is refused by config validation, as `invalidHost`, which blocks proxy start like the tunnel's port fields. A Unicode name's message gives its punycode spelling. Before this decision such a host reached the CONNECT line as raw bytes; on this branch's third round it was refused only at connect time. An empty host is a row not yet typed into and passes.
- A third upstream pool exists beside the client listener's and the tunnels'. It takes the same `maxConnections` and pending-auth-handshake limits from the config as the other two, each counted for itself, so the process can hold that many more upstream connections. In practice the route's 64-connection listener bounds it. Its `upstream.*` events carry `pool=doh`, and the tunnels' pool now carries `pool=tunnels`; the client listener's pool is unlabelled, as before.
- An upstream that blocks DoH by policy stays closed-circuit in the route's pool and is asked again on every tunnel. The cost is one refused CONNECT per upstream and tunnel, limited by the DoH race itself. `dns.doh_upstream_route_failed` reports it once a minute.
- The origin resolver shares one session per route across a resolution, with one connection per host. A resolution opens at most one tunnel per provider on the upstream route, where it opened two.
- Caps and collections: the route's listener holds at most 64 connections (`DoHUpstreamRoute.maximumConnections`), and it tracks the connections it accepted, at most those 64, so that its stop can close them. A full listener reports `connection.inbound_limit_rejected` at most once every 10 s. The used and failed events are limited to one a minute per target by a 64-entry `RuntimeEventRepeatGate`. Their targets are the configured providers' own host and port, so they take one entry per provider, and every refusal shares one entry, whatever it asked for. It reuses the SOCKS listener's 10 s handshake deadline. Each `CONNECTCoordinator` reports `connection.tunnel_target_rejected` at most once a minute for every target together, with `suppressed=`, through a `RuntimeEventRepeatGate` of its own; it uses one entry of that gate's 64.
- A local process can open a tunnel to a configured DoH provider through the upstream without the client routing rules being consulted. It cannot reach anything else through this listener: the upstream is asked only for a provider's host and port as the config writes them, and no byte of the request reaches the CONNECT.
- A plain `http://` provider is carried too, as a tunnel to its port 80. Most upstreams refuse that, and the route then reports `dns.doh_upstream_route_failed`.
- The guard does not see every proxy challenge. For a proxy that offers only Negotiate, CFNetwork raises no challenge: it tries the user's Kerberos ticket by itself and fails the request, with no prompt (measured on macOS 26). Offered Negotiate, NTLM and Basic together, it hands the delegate NTLM. No DoH route names a proxy that asks, so this limits only the backstop. CFNetwork reports that failure as error 310 with no status, so the "all DoH providers failed" warning names a proxy that refused the tunnel and says it cannot tell a Negotiate-only 407 from a policy block.
- An update download through an authenticating system proxy behaves as it did before this decision.

## Invariants and verification

- No DoH route names an upstream proxy to `URLSession`, and the upstream route exists only with an enabled upstream: `DoHSessionFactoryTests`.
- With the client rules sending the provider DIRECT and direct a black hole, a lookup is answered through an upstream that demands authentication, after Conduit answers its 407; without the route the same lookup fails: `DoHUpstreamRouteTests` and pm-sim `dns-doh-upstream-407`. Both run the real listener, `CONNECTCoordinator`, `ConnectionPool` and authenticator seam against a fake upstream. The provider is plain HTTP, because no TLS server is available to the tests.
- An `https` provider reaches the upstream as an authenticated `CONNECT` to its port 443, and the session's TLS handshake arrives through the tunnel: `DoHUpstreamRouteTests.testAnHTTPSProviderReachesTheUpstreamAsAnAuthenticatedTunnelCarryingTLS`.
- The route refuses a target that is not a provider endpoint, reports a failing upstream, is withheld while the host says so, and closes with the forwarder: `DoHUpstreamRouteTests`.
- A request for the provider with a CR, LF, NUL, tab or space and more after its address, or in a short, hex, octal or numeric form, is refused and dials nothing; an admitted request is dialled as the configured provider, keyed and reported under that one spelling: `DoHUpstreamRouteTests.testOnlyTheProvidersOwnSpellingIsAdmittedAndNothingRidesAlongWithIt`, `testAnAdmittedRequestIsDialledAsTheConfiguredProvider`, `testAProviderNameIsDialledInTheConfigsSpelling`, and `DoHSessionFactoryTests.testTheRouteDialsTheConfiguredProvidersOwnAuthority`.
- No listener writes a CONNECT whose target holds a CR, LF, space, tab, NUL, other control, DEL or non-ASCII byte: `CONNECTTargetValidationTests`, for the coordinator, the client SOCKS listener and the HTTP listener. Seven refused targets produce one event, and the next one a minute later reports `suppressed=6`.
- A port tunnel's Unicode or CR LF remote host is refused at the config boundary, with the punycode spelling for the Unicode one: `ConfigArchitectureTests.testATunnelRemoteHostIsHostText`.
- A 403 from the healthy upstream stands, with the other upstream in its backoff never dialled: `TunnelSelectionTests.testAFailoverAsksNoUpstreamInItsBackoff`.
- A tunnel given up between its selection and its dial, and one whose dial is refused after its caller gave it up, give back the probe slot they claimed and charge nothing; the next request probes that upstream and its refused dial reopens the breaker: `TunnelSelectionTests.testATunnelGivenUpBeforeItsDialFreesTheProbeItClaimed` and `testADialRefusedAfterTheStopFreesTheProbeItClaimed`.
- A PAC-chain tunnel given up on an upstream leaves another tunnel's probe on it held, so the next request does not probe it a second time: `TunnelSelectionTests.testAnAbandonedAttemptLeavesAnotherAttemptsProbeHeld`.
- A stop that lands as a dial is admitted to the pool still closes that dial, and no tunnel opens: `TunnelSelectionTests.testAStopLandingAsTheDialIsAdmittedClosesIt`.
- An upstream with a warmed fast score that answers 403 does not keep a working one with no score from carrying every tunnel: `CONNECTFailoverTests`.
- Two upstreams that answer 403 for the provider leave the tunnels' pool with the breaker state and the preferred upstream it had, and open no breaker in the route's pool. With both of the route pool's breakers open, a lookup forces the longest-open one into a probe, the 403 frees that probe under `pool=doh`, and the failover dials no upstream still in its backoff. A 5xx opens breakers in the route's pool only, reported with `pool=doh`. A flap recovery closes them: `DoHUpstreamPoolIsolationTests`, `AnsweredStatusAccountingTests` and pm-sim `dns-doh-upstream-refused`, on the real runtime.
- A flap recovery, a reconnect after an outage and a wake recovery close the tunnels' pool's breakers too: `UpstreamPoolFlapResetTests`.
- A forwarder stop closes an established tunnel on both sides, a connection still in its handshake, and a connection waiting on its upstream together with the upstream connection opened for it. A request read after the stop began dials nothing. With the first upstream's CONNECT unanswered, a stop leaves the second upstream with nothing sent to it: `DoHUpstreamRouteTests`.
- A refused target is reported as one printable token, and seventy refusals for seventy names produce one event: `DoHUpstreamRouteTests.testRefusalsAreReportedOnceAMinuteWithThePrintableTarget`.
- Each spelling of a provider's host is admitted and nothing else is, and a provider on this machine is recognised from its parsed address: `DoHSessionFactoryTests`. A provider configured by name reaches the upstream through the real listener in the spelling CFNetwork sends: `DoHUpstreamRouteTests.testAProviderConfiguredByNameIsCarriedThroughTheRealListener`.
- One origin resolution opens one authenticated tunnel for a provider: `DoHUpstreamRouteTests.testAnOriginResolutionOpensOneTunnelForAProvider`.
- A Negotiate-only proxy on a route is named in the warning as a refused tunnel: `ProxyChallengeRefusalTests.testTheAllProvidersFailedWarningNamesAProxyThatRefusedTheTunnel`.
- Every session `DoHSessionFactory` builds, every session a running forwarder holds, and the PAC download delegate cancel a proxy challenge of each scheme. These tests send no request. Each test that lets a loopback proxy answer 407 first checks the session it is about to use the same way, and sends nothing if the guard is missing, so a regressed guard cannot open the dialog on the machine running the tests: `ProxyChallengeRefusalTests` and `ProxyChallengeCanary`. pm-sim puts no 407 in front of a `URLSession`.
- NTLM, Basic and Digest, each offered alone, are cancelled and reported under their own `method=`. A server challenge keeps default handling. A PAC refresh through a challenging proxy reports the refusal in `pac.refresh_failed`: `ProxyChallengeRefusalTests`.
- Disproved by: a DoH request that reaches an upstream proxy without passing through one of Conduit's listeners, a macOS proxy-credential prompt for Conduit caused by a DoH lookup or PAC download, or a lookup that fails under a full-tunnel VPN with a healthy upstream because a client rule said DIRECT.

## Implementation evidence

The routes are in [`DoHSessionFactory.swift`](../../Sources/ProxyKernel/Network/DoHSessionFactory.swift) and `DoHTransports` in [`LocalDNSForwarder.swift`](../../Sources/ProxyKernel/Network/LocalDNSForwarder.swift). The upstream route is [`DoHUpstreamRoute.swift`](../../Sources/ProxyKernel/Network/DoHUpstreamRoute.swift), on the upstream-only mode of [`SOCKS5Server.swift`](../../Sources/ProxyKernel/Proxy/SOCKS5Server.swift). The app gives it a pool of its own in [`ProxyOrchestrator.swift`](../../Sources/ProxyKernel/Proxy/ProxyOrchestrator.swift) (`dohUpstreamPool`), and `pm-dns` does in [`PMDns.swift`](../../Sources/pm-dns/PMDns.swift). The pool's 4xx rule is `AnsweredStatusAccounting` in [`ConnectionPool.swift`](../../Sources/ProxyKernel/Proxy/ConnectionPool.swift), which also holds `UpstreamSelection` and the selection rules; the probe claim is `UpstreamCircuitBreaker.ProbeClaim` in [`UpstreamCircuitBreaker.swift`](../../Sources/ProxyKernel/Network/UpstreamCircuitBreaker.swift), and host comparison is [`DoHProviderHost.swift`](../../Sources/ProxyKernel/Network/DoHProviderHost.swift). The DoH and origin-resolver sessions use `ProxyChallengeRefusingDelegate` in [`ProxyChallengeRefusal.swift`](../../Sources/ProxyKernel/Network/ProxyChallengeRefusal.swift). The PAC download has its own delegate, `PACBoundedDownload` in [`CFPACEvaluator.swift`](../../Sources/ProxyPAC/CFPACEvaluator.swift), which makes the same refusal and fails the fetch. Tests are in [`DoHSessionFactoryTests.swift`](../../Tests/ConduitTests/DoHSessionFactoryTests.swift), [`DoHUpstreamRouteTests.swift`](../../Tests/ConduitTests/DoHUpstreamRouteTests.swift), [`DoHUpstreamPoolIsolationTests.swift`](../../Tests/ConduitTests/DoHUpstreamPoolIsolationTests.swift), [`UpstreamPoolFlapResetTests.swift`](../../Tests/ConduitTests/UpstreamPoolFlapResetTests.swift), [`TunnelSelectionTests.swift`](../../Tests/ConduitTests/TunnelSelectionTests.swift) and [`ProxyChallengeRefusalTests.swift`](../../Tests/ConduitTests/ProxyChallengeRefusalTests.swift). The scenarios are in [`DoHProxyAuthScenarios.swift`](../../Sources/pm-sim/DoHProxyAuthScenarios.swift).

Does not prove: that the first full-tunnel VPN connect on a real corporate network shows no prompt with an installed build, and that public names resolve there while a rule sends the providers DIRECT. That check is the pending validation. The tests also do not show an answered lookup over TLS through the route: they show the TLS handshake entering an authenticated tunnel, and an answered lookup over plain HTTP. And they say nothing about CFNetwork's SOCKS behaviour on a macOS version other than 26. If a version resolved a provider's hostname locally before dialling the SOCKS proxy, a hostname provider would depend on the system resolver there, as it already does on the direct route. The shipped providers are IP literals. The spellings CFNetwork sends the listener for a named provider (lowercased, root dot kept, punycode) were measured on macOS 26 only. A stop does not cancel an upstream TCP connect that is already in flight. That connection completes and is closed before it joins the pool or sends a CONNECT; no test holds a loopback connect open long enough to show it, so that path rests on the fence being read under the pool's lock where the connect completes. `testAStopLandingAsTheDialIsAdmittedClosesIt` shows that lock ordering, not a connect held open.
